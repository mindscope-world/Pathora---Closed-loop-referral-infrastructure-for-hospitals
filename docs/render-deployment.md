# Deploying on Render

This sets up one **web service** (the API and the built frontend, from the `Dockerfile`) and one managed **Postgres**,
described in [`render.yaml`](../render.yaml). Render's own pages and prices change, so where this guide says *check*, look
at Render's current documentation. For day-to-day operation (alerts, backups, data-subject requests) see
[`operations.md`](operations.md).

## 1. Decide before you start

| Decision | Why it matters |
|---|---|
| **Region** (`render.yaml`, both the service and the database) | Render's regions are Oregon, Ohio, Virginia, Frankfurt and Singapore: there is **no African region**. Hosting Kenyan patient data abroad is a data-protection decision (see the hosting item in [`dpia.md`](dpia.md)); settle it before real patient data goes in. The blueprint says `frankfurt`; the database and service must match. |
| **Plan** | The web service must be an **always-on paid** plan. The SLA monitor, message sender and retention job run inside the web process; a free service that sleeps when idle would silently stop enforcing deadlines and sending reminders. *Check* current plan sizes, and whether your database plan keeps backups. |
| **Messaging provider** | `africastalking` sends real SMS/WhatsApp; `mock` **sends nothing** (it only pretends). Render will ask you to choose; do it deliberately. |
| **Exports** | Generated CSVs go to local disk, which Render wipes on every deploy. Fine for temporary files (they expire after 7 days anyway). If you need them to survive a deploy, enable the optional disk in `render.yaml`; that needs a paid plan and limits the service to one instance. |

## 2. Prepare two secrets yourself

```bash
# Encrypts every patient name and phone number. Keep a copy OUTSIDE Render (a password manager or sealed offline copy).
openssl rand -base64 32
```

> **If this key is lost or changed, every encrypted name and phone number becomes permanently unreadable.** There is no
> recovery and no rotation tool yet. Never set a different value on a running system.

`JWT_SECRET` and `COOKIE_SECRET` are generated by Render. Pick the public address now: `APP_URL` must be the final
`https://…` people will use (your own domain, or `https://<service-name>.onrender.com`). Invitation and alert emails link to
it, and the app **refuses to start** with an `http` address.

## 3. Create it

1. Merge the work to `main` (or choose the branch that contains `render.yaml` in the next step).
2. In Render: **New → Blueprint**, connect the repository, pick the branch.
3. Render shows the service and database from `render.yaml` and asks for the three values it deliberately does not store:
   `FIELD_ENCRYPTION_KEY` (the key from step 2), `APP_URL`, `MESSAGING_PROVIDER`.
4. Apply. Render builds the image, then runs `npx prisma migrate deploy` **before** the new version starts. If a
   migration fails the deploy is aborted and nothing changes. Watch the deploy logs for
   `All migrations have been successfully applied` and then `Pathora API listening`.

Optional settings go in the service's **Environment** page: `SMTP_URL` and `MAIL_FROM` (invitations, alert emails),
`LEADS_NOTIFY_EMAIL`, the `AT_*` provider credentials plus `MESSAGING_WEBHOOK_SECRET` if you chose `africastalking`,
`METRICS_TOKEN` (step 5 below needs it).

> If your plan has no pre-deploy step, remove `preDeployCommand` and set `MIGRATE_ON_START=true` instead: the container
> applies migrations before starting, and exits (without starting the app) if they fail.

## 4. Check it works

Replace `HOST` with your address. Each check says what a pass looks like.

```bash
# 1. The process is up, and can reach the database.
curl -s https://HOST/healthz          # {"status":"ok",...}
curl -s https://HOST/readyz           # {"status":"ready"}   (503 "unavailable" = cannot reach the database)

# 2. HTTPS and security headers.
curl -sI https://HOST/ | grep -iE 'strict-transport-security|content-security-policy|x-content-type-options|referrer-policy'
#   expect all four. CSP starts with: default-src 'self';script-src 'self'; ...
curl -sI http://HOST/ | head -1       # a redirect to https (Render does this)

# 3. The frontend, including a deep link (a reload on a client-side route must still load the app).
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' -H 'Accept: text/html' https://HOST/
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' -H 'Accept: text/html' https://HOST/dashboard/cases   # 200 text/html
curl -s -o /dev/null -w '%{http_code}\n' https://HOST/assets/does-not-exist.js                                 # 404, not a page
```

**5. The client's real address (do not skip).** Every per-IP limit (sign-in, the public form, failed API keys) depends on
the app seeing each visitor's real address. Render puts proxies in front of the service, and **how many is something to
confirm, not assume.** Set a `METRICS_TOKEN` (`openssl rand -base64 32`) on the service, redeploy, then:

```bash
TOKEN=...   # the value you set
curl -s https://ifconfig.me ; echo                                   # your real public address
curl -s -H "Authorization: Bearer $TOKEN" https://HOST/diagnostics/client-ip
curl -s -H "Authorization: Bearer $TOKEN" -H 'X-Forwarded-For: 1.2.3.4' https://HOST/diagnostics/client-ip   # try to forge it
```

| What `ip` shows | Meaning | Fix |
|---|---|---|
| **Your** public address, both times | Correct | none |
| A Render or CDN address (not yours) | `TRUST_PROXY` is too low: every visitor looks the same, so limits trip for everyone together | raise `TRUST_PROXY` by 1, redeploy, repeat |
| `1.2.3.4` (the forged value) | `TRUST_PROXY` is too high: visitors can forge their address and dodge the limits | lower it by 1, redeploy, repeat |

```bash
# 6. Background jobs are running (a few minutes after start). Each lag is seconds since the job last succeeded.
curl -s -H "Authorization: Bearer $TOKEN" https://HOST/metrics | grep -E 'pathora_db_up|pathora_job_lag_seconds'
#   expect pathora_db_up 1 and a small lag for sla_monitor, message_worker, export_worker, report_scheduler
```

7. **First account.** Open the site and sign up: that creates the organisation and its first Programme Manager. Do **not** run
   the demo seed on production. In your browser's developer tools the refresh cookie should be `Secure`, `HttpOnly`, `SameSite=Strict`.
8. **Exports and audit.** Create a referral and an export from the dashboard; download it. In the Audit view choose
   *Verify integrity*; it should report an intact chain.
9. **Messaging and email** (if configured): send a message to your own number; send a team invitation to yourself.
   With `MESSAGING_PROVIDER=mock`, nothing is sent; that is expected.
10. **Backups.** Confirm in Render that backups are enabled for your database plan and how far back you can restore. Then prove a
    restore works: [`operations.md`](operations.md#backups-and-the-restore-drill) (run `scripts/backup-restore-drill.sh` against a restored copy).

## 5. Things to know

- **Rollbacks.** Render can roll the service back to a previous deploy, but **database migrations are not rolled back**. Keep
  migrations compatible with the previous version, as they are today (they only add).
- **One instance.** The app is built to be safe with several instances, but exports on local disk are not shared between them,
  so stay at one instance until exports move to object storage (not built yet).
- **A wrong database name is not an error.** Prisma's migrate step *creates* a database that does not exist, so a mistyped
  name in `DATABASE_URL` gives you a working but empty database rather than a failed deploy. The blueprint wires
  `DATABASE_URL` from the Render database for you; if you ever override it by hand, double-check the name.
- **Changing `APP_URL`** (for example when you attach a custom domain) means updating it in the dashboard and redeploying.
- **Logs** are JSON with credentials and patient fields redacted. Use Render's log streams to forward them.
- **Not covered here:** MFA, a web application firewall, and an independent penetration test: see the known gaps in
  [`security-checklist.md`](security-checklist.md).
