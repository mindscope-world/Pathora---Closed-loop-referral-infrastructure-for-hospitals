# Deploying on Railway

This sets up one **service** (the API and the built frontend, from the `Dockerfile`) and one **Postgres** database in a
single Railway project. The build, migration and health-check settings live in [`railway.json`](../railway.json); Railway
has no file that creates the database or holds variables, so those two are set up in the dashboard (sections 3 and 4).
Railway's own pages and prices change, so where this guide says *check*, look at Railway's current documentation. For
day-to-day operation (alerts, backups, data-subject requests) see [`operations.md`](operations.md).

## 1. Decide before you start

| Decision | Why it matters |
|---|---|
| **Region** (service settings, and the database's) | Railway's regions are US West, US East, EU West (Amsterdam) and Southeast Asia (Singapore): there is **no African region**. Hosting Kenyan patient data abroad is a data-protection decision (see the hosting item in [`dpia.md`](dpia.md)); settle it before real patient data goes in. Put the service and the database in the same region. |
| **Plan** | The service must run **continuously**. The SLA monitor, message sender and retention job run inside the web process; a service that sleeps when idle would silently stop enforcing deadlines and sending reminders. Do **not** enable *App Sleeping* (Serverless). *Check* current plan limits, and whether your database keeps backups. |
| **Messaging provider** | `africastalking` sends real SMS/WhatsApp; `mock` **sends nothing** (it only pretends). Choose deliberately. |
| **Exports** | Generated CSVs go to local disk, which Railway wipes on every deploy. Fine for temporary files (they expire after 7 days anyway). If you need them to survive a deploy, attach a volume (section 5); that limits the service to one replica. |

## 2. Prepare the encryption key yourself

```bash
# Encrypts every patient name and phone number. Keep a copy OUTSIDE Railway (a password manager or sealed offline copy).
openssl rand -base64 32
```

> **If this key is lost or changed, every encrypted name and phone number becomes permanently unreadable.** There is no
> recovery and no rotation tool yet. Never set a different value on a running system.

`JWT_SECRET` and `COOKIE_SECRET` are generated by Railway (section 3).

**`APP_URL` must exactly match the address people type in the browser.** This is the one setting that can lock everyone out:

- The app answers any request that carries an `Origin` header different from `APP_URL` with **`403 CORS_DENIED`**, and
  browsers send that header when signing in. So if `APP_URL` is wrong, **sign-in fails for everyone**, not just emails
  linking to the wrong place. (Invitation and alert emails also link to `APP_URL`.)
- "Exactly" means the same **scheme, host and port**. `https://pathora.example` and `https://www.pathora.example` are
  different addresses; so are `http` and `https`. A trailing slash does not matter.
- It must be `https://…` in production; the app **refuses to start** with an `http` address.

Which address? Either your own domain, or the one Railway gives the service, `https://<name>.up.railway.app`. Generate it
first (section 3, step 3) and then paste the real address as a literal value, e.g.
`https://pathora-production.up.railway.app`. (`https://${{RAILWAY_PUBLIC_DOMAIN}}` also works, but if it is not substituted
the app refuses to start with `APP_URL: must be https in production`, so the literal address is the safer choice.)
Until it matches what is in the browser, sign-in returns 403.

## 3. Create it

1. Merge the work to `main` (or choose the branch that contains `railway.json`).
2. In Railway: **New Project → Deploy from GitHub repo**, pick the repository and branch. Railway reads `railway.json`
   and builds the `Dockerfile`. The first deploy will fail its health check until the database and variables exist; that
   is expected.
3. On the service, **Settings → Networking → Generate Domain** (or add your own domain). Set the region under **Settings**.
4. In the same project: **New → Database → Add PostgreSQL**. Check the version is 16 (what docker-compose and CI use).
5. On the web service, open **Variables → Raw Editor** and enter:

   ```
   DATABASE_URL=${{Postgres.DATABASE_URL}}
   JWT_SECRET=${{secret(48, "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789")}}
   COOKIE_SECRET=${{secret(48, "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789")}}
   FIELD_ENCRYPTION_KEY=<the key from section 2>
   APP_URL=https://<your-service>.up.railway.app
   MESSAGING_PROVIDER=mock
   PORT=4000
   HOST=0.0.0.0
   TRUST_PROXY=1
   LOG_LEVEL=info
   ```

   `Postgres` is the database service's name; change it if you renamed it. The two secrets must be different from each
   other. Set `MESSAGING_PROVIDER=africastalking` only when you mean to send real messages. Use your own domain in
   `APP_URL` instead if you attach one. If the logs show `Invalid environment configuration`, a variable is missing or
   `APP_URL` does not start with `https://`.
6. **Deploy.** Railway builds the image, then runs `npx prisma migrate deploy` **before** the new version starts. If a
   migration fails the deploy is aborted and the previous version keeps serving. Watch the deploy logs for
   `All migrations have been successfully applied` and then `Pathora API listening`. Railway only switches traffic over
   once `/readyz` returns 200.

Optional variables: `SMTP_URL` and `MAIL_FROM` (invitations, alert emails), `LEADS_NOTIFY_EMAIL`, the `AT_*` provider
credentials plus `MESSAGING_WEBHOOK_SECRET` if you chose `africastalking`, `METRICS_TOKEN` (check 5 in section 4 needs it).

> If the pre-deploy step is not available to you, remove `preDeployCommand` from `railway.json` and set
> `MIGRATE_ON_START=true` instead: the container applies migrations before starting, and exits (without starting the app)
> if they fail.

## 4. Check it works

Replace `HOST` with your address. Each check says what a pass looks like.

```bash
# 1. The process is up, and can reach the database.
curl -s https://HOST/healthz          # {"status":"ok",...}
curl -s https://HOST/readyz           # {"status":"ready"}   (503 "unavailable" = cannot reach the database)

# 2. HTTPS and security headers.
curl -sI https://HOST/ | grep -iE 'strict-transport-security|content-security-policy|x-content-type-options|referrer-policy'
#   expect all four. CSP starts with: default-src 'self';script-src 'self'; ...
curl -sI http://HOST/ | head -1       # a redirect to https (Railway does this)

# 3. The frontend, including a deep link (a reload on a client-side route must still load the app).
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' -H 'Accept: text/html' https://HOST/
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' -H 'Accept: text/html' https://HOST/dashboard/cases   # 200 text/html
curl -s -o /dev/null -w '%{http_code}\n' https://HOST/assets/does-not-exist.js                                 # 404, not a page
```

**5. The client's real address (do not skip).** Every per-IP limit (sign-in, the public form, failed API keys) depends on
the app seeing each visitor's real address. Railway puts a proxy in front of the service, and **how many there are is something to
confirm, not assume.** Set a `METRICS_TOKEN` (`openssl rand -base64 32`) on the service, redeploy, then:

```bash
TOKEN=...   # the value you set
curl -s https://ifconfig.me ; echo                                   # your real public address
curl -s -H "Authorization: Bearer $TOKEN" https://HOST/diagnostics/client-ip
curl -s -H "Authorization: Bearer $TOKEN" -H 'X-Forwarded-For: 1.2.3.4' https://HOST/diagnostics/client-ip   # try to forge it
```

| What `ip` shows | Meaning | Fix |
|---|---|---|
| **Your** public address, both times | Correct | none |
| A Railway or CDN address (not yours) | `TRUST_PROXY` is too low: every visitor looks the same, so limits trip for everyone together | raise `TRUST_PROXY` by 1, redeploy, repeat |
| `1.2.3.4` (the forged value) | `TRUST_PROXY` is too high: visitors can forge their address and dodge the limits | lower it by 1, redeploy, repeat |

```bash
# 6. Background jobs are running (a few minutes after start). Each lag is seconds since the job last succeeded.
curl -s -H "Authorization: Bearer $TOKEN" https://HOST/metrics | grep -E 'pathora_db_up|pathora_job_lag_seconds'
#   expect pathora_db_up 1 and a small lag for sla_monitor, message_worker, export_worker, report_scheduler
```

7. **First account.** Open the site and sign up (a `403` with `CORS_DENIED` here means `APP_URL` does not match the address in
   your browser: see section 2): that creates the organisation and its first Programme Manager. Do **not** run
   the demo seed on production. In your browser's developer tools the refresh cookie should be `Secure`, `HttpOnly`, `SameSite=Strict`.
8. **Exports and audit.** Create a referral and an export from the dashboard; download it. In the Audit view choose
   *Verify integrity*; it should report an intact chain.
9. **Messaging and email** (if configured): send a message to your own number; send a team invitation to yourself.
   With `MESSAGING_PROVIDER=mock`, nothing is sent; that is expected.
10. **Backups.** Confirm in Railway that backups are enabled for the database (check the Postgres service's *Backups* tab and your plan) and how far back you can restore. Then prove a
    restore works: [`operations.md`](operations.md#backups-and-the-restore-drill) (run `scripts/backup-restore-drill.sh` against a restored copy).

## 5. Things to know

- **Rollbacks.** Railway can redeploy a previous deployment, but **database migrations are not rolled back**. Keep
  migrations compatible with the previous version, as they are today (they only add).
- **One replica.** The app is built to be safe with several instances, but exports on local disk are not shared between them,
  so stay at one replica (`numReplicas` in `railway.json`) until exports move to object storage (not built yet).
- **Optional volume for exports.** Attach a volume to the service with mount path `/data`, and set `RAILWAY_RUN_UID=0` so the
  container can write to it (the image runs as a non-root user and Railway mounts volumes as root). Exports are already
  written to `/data/exports`. A volume also means a brief gap on each deploy, because two instances cannot mount it at once.
- **A wrong database name is not an error.** Prisma's migrate step *creates* a database that does not exist, so a mistyped
  name in `DATABASE_URL` gives you a working but empty database rather than a failed deploy. `${{Postgres.DATABASE_URL}}`
  points at the right one; if you ever override it by hand, double-check the name.
- **Changing `APP_URL`** (for example when you attach a custom domain) means updating it under **Variables** and redeploying.
  From that moment the old address stops working for sign-in, so switch your users over at the same time. Links already
  sent in emails keep pointing at the old address.
- **Logs** are JSON with credentials and patient fields redacted. Use Railway's log drains or the Observability tab to forward them.
- **Not covered here:** MFA, a web application firewall, and an independent penetration test: see the known gaps in
  [`security-checklist.md`](security-checklist.md).
